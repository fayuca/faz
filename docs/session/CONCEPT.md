### OBJECTIVES
* A job.
* A full vertical slice: DB | Spring Boot | React
* Backend only features a single transactional object: Transaction, which touches upon all of the backend facilities: DTOs, repositories, services, etc. More objects could follow, it's a matter of what helps the demo.
* Frontend is a normal demo frontend with CRUD and such, and will also include a section like a lite swagger to demonstrate the API arquitecture.
* Apply some user facing shape for the demo other than just a bunch of filters, tables and api calls. What _are_ this transactions? Is this a personal budget app? Is it business?
* Deployment.

### VICES, PROPER ARQUITECTURE, LEARNING
I have 15+ years of experience with Java EE, but codebases are never uniform and teams also develop internal habits, so my knowledge of components proper is rather spotty, eg. Spring, as it came to me only in so far as I had to apply it to work. I believe this is the case for most teams, though, it is natural for real codebases to create idiosyncratic uses of tech stacks, and to walk away from standards that, while useful, simply doesn't match their use case or dynamic.
I've been using this demo to re-learn the fundamentals and to adopt good practices. We should continue building with this learning approach, This helps to prepare for presenting the demo, but it is a good permamnent attitude with projects so as to realign one's own knowledge properly, adopt standard practices, and get rid of vices.
